# PushAll 消息中心 · 设计方案（v0.1 讨论稿）

> 目标：跨平台桌面应用（Windows / macOS / Linux），以"配置"而非"写代码"的方式，
> 从 SQL、HTTP、文件、事件等来源取数，格式化后推送到钉钉、企业微信、飞书、邮件等下游。
> 来源与下游均为**插件**，可安装、可禁用、可自行扩展。

---

## 1. 目标与边界

### 要做
- 一套可复用的「场景」：取数 → 处理 → 渲染 → 路由 → 推送。
- 数据源、模板、渠道三者解耦、可复用；一个场景可推多个渠道。
- 插件化：新增一个来源/下游，只加一个插件包，不改主程序、不改前端。
- 全链路可观测：每次运行能看到取数耗时、原始数据、渲染结果、渠道响应。
- 单机可用（本地桌面），也能以服务形态部署给团队共用（同一套代码）。

### 暂不做（v1）
- 复杂 DAG/分支编排画布（先做表单式步骤编辑，画布放 v2）。
- 多租户、细粒度 RBAC（v1 单用户 + 可选访问令牌）。
- 消息双向交互（如钉钉卡片按钮回写），v2 再考虑。

## 2. 同类产品与可借鉴点

| 产品 | 定位 | 可借鉴 | 不适合直接用的原因 |
|---|---|---|---|
| **n8n** | 节点式自动化编排 | 节点/连接、执行历史、凭据管理、插件生态 | 偏通用工作流，学习成本高；消息中心场景过重 |
| **Node-RED** | 流式 IoT 编排 | 可视化连线、节点即插件、调试面板 | 同上，UI 偏工程化 |
| **Huginn** | 定时抓取 + 事件 + 推送 | Agent 模型（抓取/过滤/推送分离）、定时任务 | 老派 UI，无桌面端 |
| **Home Assistant** | 集成（Integration）体系 | 配置流（Config Flow）、集成清单、设备/实体抽象 | 面向 IoT，非消息场景 |
| **Apprise** | 统一推送库 | 200+ 下游的统一下发抽象、URL 式配置 | 只是库，无 GUI/调度/模板 |
| **Grafana Alerting / Kibana Watcher** | 查询 + 阈值 + 通知 | 查询模板、告警规则、通知渠道、静默 | 绑定各自数据平台 |
| **阿里云 EventBridge / AWS SNS** | 企业消息总线 | 事件模型、订阅路由、投递重试与死信 | 云服务，不可私有化定制 |

**结论**：形态上最接近「n8n 的编排 + Huginn 的定时取数 + Apprise 的渠道抽象」，
但收敛到"消息"这一个垂直场景，配置更少、开箱即用。

参考链接：
- n8n — https://n8n.io
- Node-RED — https://nodered.org
- Huginn — https://github.com/huginn/huginn
- Apprise — https://github.com/caronc/apprise
- Home Assistant Integrations — https://developers.home-assistant.io/docs/creating_integration_manifest

## 3. 技术选型

### 方案对比

| | A. Python 内核 + Web UI + 桌面壳（推荐） | B. Tauri 2 + React + Python sidecar | C. Electron + Node 全栈 |
|---|---|---|---|
| 界面体验 | 好（Web 技术） | 最好（原生 WebView，体积小） | 好 |
| 插件开发 | **Python，最贴合 SQL/Oracle/HTTP 场景** | Python（sidecar） | Node，Oracle 驱动较弱 |
| 跨平台打包 | PyInstaller / Nuitka，成熟 | Tauri 打包，需双运行时 | electron-builder，成熟 |
| 安装包体积 | 约 60–90 MB | 约 20–40 MB | 约 120–180 MB |
| 开发成本 | **低** | 中高（Rust + 双进程） | 中 |
| 团队复用 | 同一套代码可直接部署为内网 Web 服务 | 同左，需额外处理 | 同左 |

### 推荐：方案 A

```
┌─────────────────────────────────────────────┐
│  桌面壳（可选）：pywebview / Tauri WebView    │
│  ┌───────────────────────────────────────┐  │
│  │  Vue 3 + TypeScript + Vite（SPA）      │  │
│  └──────────────────┬────────────────────┘  │
└─────────────────────┼───────────────────────┘
                      │ http://127.0.0.1:8765
┌─────────────────────▼───────────────────────┐
│  FastAPI 内核（Python 3.11+）                │
│  ├ ScenarioService   场景/编排               │
│  ├ Scheduler         cron / 手动 / Webhook   │
│  ├ Runner            取数→渲染→路由→发送      │
│  ├ PluginHost        插件发现/加载/权限       │
│  ├ TemplateEngine    Jinja2 + 渠道适配        │
│  └ SecretVault       密钥加密/系统钥匙串      │
└───────┬───────────────────────┬─────────────┘
        │                       │
┌───────▼────────┐      ┌───────▼──────────────┐
│ Source 插件     │      │ Sink 插件             │
│ sql / http /    │      │ dingtalk / wecom /   │
│ file / webhook  │      │ feishu / email / ... │
└───────┬────────┘      └──────────────────────┘
        │
┌───────▼──────────────────────────────────────┐
│ SQLite（配置 + 运行记录）                     │
│ 敏感字段：AES/Fernet 加密；可选系统钥匙串      │
└──────────────────────────────────────────────┘
```

**为什么是 Python**：数据源侧要连 Oracle / MySQL / PostgreSQL，Python 驱动最全；
现有 OA 相关脚本（查询、ELK、导出）可以直接沉淀为插件；
桌面与服务器双形态时，后端逻辑零改动。

**为什么不直接 Electron**：Node 侧 Oracle 驱动（oracledb）可用但生态弱、安装体积大；
插件开发者（内部开发）用 Python 成本更低。

## 4. 核心概念与数据模型

```
SourceProfile（数据源连接，可复用）
        │
Scenario（消息场景 = 编排单元）
  ├ schedule    cron / 手动 / Webhook / 文件监听
  ├ pipeline    取数 → 过滤/加工 → 渲染
  └ routes      → Channel（渠道实例）×N，可带条件
        │
Template（模板，可复用，带版本）     Channel（钉钉群A / 企微群B / 邮件组）
        │                                   │
        └──────────── Run（一次执行）────────┘
                        │
                   RunStep（取数/渲染/发送 各步骤耗时与响应）
```

### 表结构（规划）

| 表 | 说明 | 关键字段 |
|---|---|---|
| `scenario` | 消息场景 | id, name, enabled, schedule_json, source_id, template_id, options |
| `route` | 场景→渠道 | scenario_id, channel_id, condition_json, priority |
| `source_profile` | 数据源连接 | id, plugin_id, name, config_json（加密） |
| `template` | 模板 | id, name, engine, title_tpl, body_tpl, version |
| `channel` | 渠道实例 | id, plugin_id, name, config_json（加密）, rate_limit |
| `plugin` | 已安装插件 | id, type, version, path, enabled, permissions |
| `run` | 运行记录 | id, scenario_id, trigger, status, row_count, duration_ms |
| `run_step` | 步骤明细 | run_id, step, status, duration_ms, request, response |
| `secret` | 密钥 | key, value_enc, updated_at |
| `setting` | 应用设置 | key, value |

### 统一消息模型

```json
{
  "message_id": "uuid",
  "scenario_id": 3,
  "title": "华北区库存低于安全线（12 家）",
  "content": "markdown 正文",
  "level": "warning",
  "tags": ["inventory", "north"],
  "data": [{"店铺": "BJ001", "库存": 3}],
  "dedup_key": "inventory:BJ001:2026-11-06",
  "created_at": "2026-11-06 09:00:03"
}
```

> 模板产出统一为 **Markdown**；各渠道适配器负责转成钉钉 markdown、企微 markdown、
> 飞书卡片、邮件 HTML，并对超长内容自动截断/分片。避免"一个渠道一套模板"。

## 5. 插件体系

### 5.1 三类插件

| 类型 | 职责 | 内置示例 |
|---|---|---|
| `source` | 取数，返回 `list[dict]` | sql（oracle/mysql/pg/sqlite）、http、file、static |
| `transform`（可选） | 过滤/字段映射/聚合/去重 | filter、map、group、dedup |
| `sink` | 发送消息 | dingtalk、wecom、feishu、email、webhook、file |

### 5.2 插件目录与清单

```
plugins/
  source_oracle/
    manifest.json        # 元信息 + 入口 + 权限
    plugin.py            # 实现类
    schema.json          # 配置表单由它自动生成
    icon.svg
```

```json
{
  "id": "source.oracle",
  "type": "source",
  "name": "Oracle 数据库",
  "version": "1.0.0",
  "entry": "plugin.py:OracleSource",
  "config_schema": "schema.json",
  "permissions": ["database"]
}
```

### 5.3 接口（示意，非最终实现）

```python
class SourcePlugin(Protocol):
    def test(self, config: dict) -> TestResult: ...
    def fetch(self, config: dict, ctx: RunContext) -> list[dict]: ...

class SinkPlugin(Protocol):
    def test(self, config: dict) -> TestResult: ...
    def send(self, message: Message, config: dict, ctx: RunContext) -> SendResult: ...
```

`RunContext` 提供：日志、超时、取消信号、密钥解析（`secret://xxx`）、HTTP 客户端。

### 5.4 关键设计：表单由 Schema 驱动

插件自带 `schema.json`（JSON Schema + `ui:widget` 扩展），前端渲染成表单：

```
插件清单 ──► /api/plugins ──► 前端渲染配置表单
                                  ├── 普通字段：input / select / switch
                                  ├── 密钥字段：password + 钥匙串存储
                                  ├── SQL 字段：代码编辑器（Monaco）
                                  └── 测试按钮：调用插件 test()
```

**新增插件不需要改前端**，这是插件体系能否长期维护的关键。

### 5.5 插件生命周期与安全

- 安装：本地目录 / zip / Git 仓库；校验 manifest 与版本。
- 启用/禁用：禁用后其配置仍保留，场景引用时给出明确提示。
- 权限声明：`network` / `database` / `filesystem`；越权调用直接拒绝并记审计日志。
- 隔离：v1 同进程 + 超时/异常兜底；v2 子进程执行，崩溃不影响主进程。
- 升级：保留旧版本，失败可回滚。

## 7. 功能清单

### v1（可用）
- 场景 CRUD、启用/禁用、复制。
- 内置数据源：Oracle / MySQL / PostgreSQL / SQLite / HTTP / 静态数据。
- 模板：Jinja2 语法 + `md_table` 等过滤器 + 样例数据实时预览。
- 内置渠道：钉钉群机器人（含加签）、企业微信群机器人、飞书、SMTP 邮件、通用 Webhook。
- 触发：cron 定时、手动、外部 Webhook 调用。
- 运行记录：状态、行数、耗时、渲染内容、渠道响应、失败原因。
- 试运行（只渲染不发送）。
- 密钥加密存储；可选访问令牌。
- 插件：目录扫描 + 启用/禁用 + Schema 表单 + 测试连接。
- 桌面壳 + 本地数据目录；数据备份/恢复（导出 zip）。

### v2（好用）
- 流程画布（节点连线）作为高级编辑模式。
- 条件路由：按数据内容/级别/tag 选择渠道；渠道组、降级渠道。
- 去重窗口、限流、失败重试队列、死信与补发。
- 入站 Webhook 触发 + 参数映射。
- 模板版本管理与对比；渠道级模板覆盖。
- 插件市场页（本地 zip / Git / 内网源），签名校验。
- 多用户与权限（管理员/编辑/只读）、操作审计。
- 企业微信应用消息、钉钉工作通知、飞书应用消息（不仅是群机器人）。

### v3（平台化）
- 分布式 Worker、多实例调度、任务分片。
- 消息统计报表、SLA、告警升级策略。
- 与 OA 流程/事件总线集成（如泛微流程归档事件直接触发）。
- 开放 API / SDK，供其他系统注册场景。

## 8. 非功能设计

| 维度 | 设计 |
|---|---|
| 安全 | 敏感字段 Fernet 加密；可选系统钥匙串；插件权限声明；API Token；审计日志 |
| 可靠 | 每次发送独立事务记录；失败重试（指数退避）；幂等键防重复；进程崩溃可恢复未完成任务 |
| 性能 | 单场景默认上限 1000 行；大结果集转附件/链接；模板渲染超时 5s；渠道并发限流 |
| 可观测 | 运行时间线、请求/响应原文、成功率与耗时统计、日志导出 |
| 可移植 | 配置与数据存本地 SQLite；一键导出/导入；不依赖外部服务即可运行 |
| 兼容 | Windows 10+ / macOS 12+ / Linux（deb、AppImage） |
